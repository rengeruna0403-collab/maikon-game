## ゲーム開始時の状況

プレイヤーは「舞昆茶屋」を**祖父から引き継いだ**経営者。
ゼロから起業したのではなく、すでに存在するお店・物件・商品ラインナップを受け継いだ状態でゲームが始まる。

### 引き継いだもの

| 項目 | 状態 |
|------|------|
| 舞昆茶屋（イートイン・商品販売） | 閉店中。再開が最初のミッション |
| 舞昆の商品ラインナップ | 祖父が仕入れていた商品が棚に並んでいる（取扱中） |
| 物販チャネル（祖父の販路） | 既存の得意先・取引先が継続中。売上は入ってくる |
| アパート（物件） | 空室あり。入居者募集が最初のミッション |
| 地域との関係 | 祖父の代からのご縁があるが、プレイヤー自身はまだ顔が知られていない |

### 引き継いでいないもの（プレイヤーが新たに作るもの）

- お客様との個人的なご縁（常連・関係）
- 店のメニュー構成（祖父の時代と変えてよい）
- 経営の方向性・戦略

---

## 設定の軸：「知っているようで、知らない」

プレイヤーは子どもの頃から舞昆が身近にあった。
しかし「舞昆とは何か」「なぜお客様に喜ばれるのか」を自分の言葉で語れない。
第1章「舞昆って何？」はこの"知っているつもり"から本当の理解へ向かう物語。

### ストーリーへの使い方の原則

商品効果の断定ではなく、主人公が経営を通じて疑問を持ち学んでいく構造にする。

```
経営 → 疑問 → 学習 → 舞昆への理解 → 次の経営目標
```

「舞昆を食べれば○○になる」という商品効果説明にしない。  
監修済み情報だけを「舞昆ノート」等へ段階的に追加できる設計が望ましい。

## ブランド監修リスト（Review Required）

ゲーム内でブランド「舞昆」に関する情報を使用する前に、必ずこのリストで状態を確認すること。
状態が「承認済み」のもの以外はゲーム本文・イベント・ストーリーへ記載しない。

**状態の定義：**
- `承認済み` — 公開情報として確認済み。使用可能
- `要監修` — 事実の可能性があるが未確認。**使用禁止**
- `創作` — ゲームオリジナル。実在人物・事実との混同禁止
- `使用禁止` — 誤解・法的リスクがあるため永久禁止

### オーナー接客状態（確定仕様）

`G.staffUnavailableToday`（配列）に欠勤スタッフ名を格納する。日送り（`advanceDay()` finally ブロック）でリセットされ翌日は通常復帰。イベント effect キー `staffOff:'スタッフ名'` で設定する。

## スタッフ運営ルール

### みどりの成長フェーズ

みどりの行動・提案は、採用からの経過期間・研修履歴・月次営業経験に応じて段階的に解放する。

| フェーズ | 記号 | 目安 | 行動範囲 |
|---|---|---|---|
| 基礎習得 | A | 〜採用30日 | 接客を覚える・店の流れを理解する・オーナーに相談する。不安の相談・接客指導を受ける |
| 少し先輩になる | B | 第2スタッフ加入後7日以上 | 「自分が教えてもらったことを伝える」レベル。先輩として支えるのではなく "少し先に入ったスタッフとして力になる" |
| 自主的な改善 | C | 採用30〜60日 | 自分で工夫する・常連客の反応に気づく・小さな改善提案。ギフト包装提案・クレーム対応の試み |
| 分析・運営 | D | 採用60日以上＋研修済み＋月末1回以上 | 売上傾向を観察する・メニュー改善案を出す |
| 育成・マネジメント | E | 採用210日以上＋level≥3 | 他スタッフの正式育成担当・昇格相談・店舗運営を任される |

**Bフェーズの重要注意事項：**
- `staff_new_training`（さくらへの声がけ）はBフェーズ。"新人教育担当" ではなく "少し先輩として支える" として扱う
- B相当のイベントに、E相当の肩書き・責任（「主任候補として正式に認める」等）を混入させない
- Bフェーズのみどりの発言は「私が教えてもらったことを伝えたい」「力になれたらと思って」など自分の経験を共有する表現にとどめる

**実装ルール（コード上の制約）：**

- **採用直後は基礎業務習得フェーズ**。分析・提案・改善を行うイベントは採用直後に発生させない
- **自主分析・改善提案は一定勤務期間＋研修（`midori_growth` 解決済み）後**に解放する
- **「先月」「これまで」「最近のお客様の傾向」等の時間表現は、実際の経過月数と一致させる**。`monthlyTick` を1回以上経験していない状態（ゲーム開始4月中）で「先月」は使わない
- **高度なスタッフ行動（売上分析・発注業務・新人指導・数値管理）は後期フェーズへ配置する**
- 商品別売上データが存在しない場合は「43%」「集計したら〇〇」等の実測風断定表現を使わず、観察ベースの表現（「〜のお客様が多い気がする」「〜はあまり手が出ていないみたい」）を使う

## 入居者の退去ルール

- 退去案件（`early_departure`）は、入居者が1室以上存在する場合のみ発生する（`requireTenant:true`）
- 対象入居者は案件**生成時**に固定する（満足度最低の入居中部屋を選定）。選択時に再選定しない
- 現行ゲームでは退去予定期間を持たず、「退去手続きを速やかに進める」を選択した瞬間に即時退去となる
- 案件本文は即時退去ロジックに合わせた表現にする。「来月末で退去」等の未来日付を書かない
- 退去後の部屋は空室・未募集状態（`tenant=null, seeking=false`）になる
- 再募集はプレイヤーが物件画面から判断して開始する（自動で `seeking=true` にしない）
- 原状回復システムは現時点では未実装。案件本文に原状回復を要求する表現を書かない
- 「住み続けられないか相談する」は「今回は退去を見送ってもらえた」扱いであり、永続居住を保証しない
- 引き止め成功後90日は同じ部屋の入居者を `early_departure` 対象から除外する（`_departureHoldUntil` フィールド）
- 入居者満足度（`r.satisfaction`）は `early_departure` の**発生確率**には影響しない。生成後の**対象選定**にのみ使われる（最低満足度の部屋を選ぶ）

## conditionOnly案件の日次分散設計（v1.3i）

`generateConditionCases()`は毎日実行され、条件を満たしたすべての案件が即時addCase()されていた。
Day30境界（`midori.daysWorked === 30`）では複数案件が同日に発火し、ケースボックスが過密になる問題があった。

### 基本方針

条件がSTABLEな案件（翌日も同条件を満たし続けるもの）は**normalCondプール**に積み、1日1件だけaddCaseする。
残りは翌日以降のgenerateConditionCases()で再評価される（条件が継続するため問題なし）。

### 優先度分類

| 優先度 | 値 | 対象案件 | 判断理由 |
|--------|---|----------|----------|
| HIGH | 2 | `narita_expansion`, `narita_first_visit`, `narita_site_visit` | 成田との主要ストーリー進行。プレイヤー体験への影響大 |
| NORMAL | 1 | `midori_jido`, `staff_new_training` | スタッフ生活描写。重要だが緊急性なし |
| LOW | 0 | `taste_midori_snack`, 商品解放案件 | 嗜好イベント・商品。遅延1〜2日は許容 |

同優先度内の順序は**配列への追加順（定義順）**で安定している（ランダム化しない）。

### CRITICAL（分散制御の対象外）

以下は即時性・緊急性があるためnormalCondプールを経由しない：

- **緊急閾値**: `midori_help`（sat<45）、`tenant_request`（入居率50%未満）、`narita_warning`（資金不足）
- **チュートリアル・ゲーム進行**: `narita_first_ad`、`narita_fullhouse_goal`
- **採用フロー**: `midori_apply`、`narita_suggest_hire`、`midori_apply_retry`
- **即日マイルストーン**: `midori_growth`（dw=14）、`narita_review`（90日おき・当日のみ）
- **季節・ランダム**: `midori_sick`、`midori_overtime`、`bento_request_*`、`menu_refresh`
- **Eフェーズ**: `staff_promotion_discuss`、`staff_want_independent`、`staff_thanks`
- **ゲーム後半**: `narita_next_location`、`narita_fork_choice`、哲学シリーズ

### VOLATILE条件の扱い

`taste_midori_snack`（`midori.satisfaction >= 70`）は翌日に満足度が低下する可能性がある（VOLATILE条件）。
初めて条件を満たした日に`G._midoriSnackEligibleDay = totalDays`を保存し、以降は満足度の変動によらずnormalCondに積む。
既存セーブデータは`_normalizeSaveData()`で補完される。

### MAX_PENDING尊重

`normalCond.dispatch`は`G.cases.filter(c => !c.resolved).length >= 6`（MAX_PENDING）のとき追加しない。
翌日以降にpending数が減少すれば自動的に処理される。

### デバッグ

`G._normalCondDebug`に当日の候補リスト・pending数・発火結果を文字列で保存する。
`G._productUnlockDebug`は商品解放候補がnormalCondに入ったことを記録する。
